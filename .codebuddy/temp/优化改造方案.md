### 0.3 本方案的判断标准（据上确立）

1. 改造是否服务于「**补组件 + 修表单 bug**」这个真实主诉？
2. 改造在**一人维护**的资源约束下是否可持续（不会腐烂）？
3. 改造是否会**拖慢当前月均 6 版本的响应节奏**？（对小库，快速响应本身即核心竞争力）
4. 改造的**隐藏回归风险**是否被明确评估并可控？
5. 零社区反馈的能力（SSR/a11y/i18n），按「**有第一个真实诉求再做**」处理，不预先投入。

## 1. 事实核查纠错记录（累计 4 处）

制定与重判过程中，对自身结论逐条复验，**共推翻 4 条错误结论**。这直接说明首轮评估的可信度需要打折，也是本方案要求「每项改造前必须先实测验证问题真实存在」的原因。

| # | 原结论 | 复验结果 | 证据 | 对方案的影响 |
|:--|:--|:--|:--|:--|
| 1 | Resolver `.pnpm` 路径在用户项目不存在，按需引入**必然失效** | ❌ 错。产物真实存在，`npm pack --dry-run` 确认 18 个 CSS **会随包发布**（887 文件 / 909.6 kB） | `find es -name main.css` 命中；pack 清单含全部 18 条 | P0→P1，后续进一步降为「不改实现，只加 CI 断言」 |
| 2 | ConfigProvider 主题注册**已有漏项** | ❌ 错。31 个 `useInject` 与 `Theme` 键**完全一致，零漏项** | `comm -13` 差集为空 | 从「已有 Bug」降为伪问题，**否决** |
| 3 | 全库 **0 个 `<style scoped>`**，样式隔离缺失 | ❌ 错。**66/66 全部 scoped** | 唯一 style 形态即 `<style lang="less" scoped>` | 样式治理范围从「全库改造」收窄为「1 行 `caret-color`」 |
| 4 | `publish.sh` **无 lint / 无门禁** | ❌ 措辞错。已有 `.husky/pre-commit`（lint-staged: prettier + eslint --fix）与 `.husky/commit-msg`（commitlint，type-enum 约束 9 种） | `cat .husky/*` | 改为「门禁不完整，仅缺 type-check 与 test」 |

**共性教训**：四处错误均源于**检索模式不精确或未实测即推断**（字面匹配漏掉变体写法；未验证产物即断言包内容；未做集合差集即断言漏项；未读 husky 即断言无门禁）。

## 2. 核心结论

**诊断大体准确，处方严重错配。**

v1 方案开的是给「企业级基础设施」的药，而病人是「371 star 的个人作品」，且病人真正的主诉（缺组件、表单 bug）**v1 一条都没接**：

| 用户在要什么 | v1 方案在给什么 |
|:--|:--|
| #43 多选下拉框 + 下拉树（Open 1 年） | 测试覆盖率 70% |
| #35 Menu + 全局主题（Open 1.4 年） | a11y 语义化重构 |
| #34 穿梭框 Transfer | i18n 机制 |
| #44/#37/#40 表单受控值 bug（同类根因） | 巨型组件拆分、ESLint 规则回收 |

**v1 方案中对齐真实用户诉求的条目数 = 0。**

**净调整**：原 7 阶段 12~16 周 → **工程侧压缩至 1~2 周**，其余资源全部投向「补组件 + 修表单类根因」。

## 3. 推荐执行方案

### 3.1 第一优先：对齐真实用户诉求（投产比最高）

| 序 | 事项 | 依据 | 说明 |
|:--:|:--|:--|:--|
| **1** | **系统性排查表单类组件受控值处理** | #44 / #37 / #40 | 三条是**同一类根因**（受控值与响应式更新时机），说明这不是三个孤立 bug 而是**一个架构性问题**。找出共性根因统一修复，并为三条建回归测试 —— **这是唯一能同时服务「修 bug」与「建测试」两个目标的切入点** |
| **2** | **补 Menu 组件** | #35，Open **1.4 年** | 67 个组件里没有 Menu 是「组件库」的明显基础缺口 |
| **3** | **补多选 Select / TreeSelect / Transfer** | #43（Open 1 年）、#34 | 高频中后台需求 |
| **4** | 全局主题能力增强 | #35 同条 | 现有 ConfigProvider 仅支持 `primaryColor`，用户诉求更广 |

> 建议以事项 1 作为切入点：它同时是 bug 修复、架构改进与测试建设，且完全对齐用户反馈。

### 3.2 A 类：工程侧刚需（约 1 周，无争议）

| 项 | 内容 | 成本 | 为什么真的有必要 |
|:--|:--|:--:|:--|
| **A-1 仓库卫生** | ①`.gitignore` 追加 `docs/.vitepress/cache` 与 `.codebuddy`；②`git rm -r --cached docs/.vitepress/cache`（38 文件）；③`scripts/*.sh` 的 `git add .` 改显式路径 | 5 分钟 | 纯收益。当前三个脚本全用 `git add .`，是缓存被反复提交的直接原因；`git status` 现显示 38 个虚假 diff |
| **A-2 已修 bug 回归用例** | 引入 `vitest` + `@vue/test-utils`，**仅**为 #44 / #37 / #40 及后续每个修复的 bug 建用例 | 2~3 天 | 每条用例都有**明确防护目标**，不会腐烂。替代 v1 的「70% 覆盖率」（那是无目标的投入，且一人维护下必然腐烂成"绿灯假象"） |
| **A-3 门禁补全** | `pre-push` 或 `publish.sh` 中串入 `type-check` + `test`；移除 `scripts/*.sh` 默认 commit message `'feat: update components library'`（强制传语义化描述） | 1~2 小时 | 已有 lint 门禁，加这两项边际成本近零。默认 message 是 2532 次提交中大量无信息量 commit 的根因 |

### 3.3 B 类：顺手做（成本极低，做了没坏处）

| 项 | 内容 | 成本 | 定位 |
|:--|:--|:--:|:--|
| **B-1 SSR 安全化** | 4 处：`Select.vue` L81-82、`Tooltip.vue` L70-71 初值改 0 + `onMounted` 赋值；`utils/index.ts` L606-607、L827 补 `typeof window === 'undefined'` 守卫（注意 `window &&` 守卫**无效**，Node 下读未声明标识符直接抛错） | 0.5 天 | **从 P0 降级为「顺手做」**：零社区反馈、文档从未声称支持 SSR。但改动小、无风险。**v1 要求的「建 Nuxt 验证工程 + 67 组件 SSR 冒烟」属过度投入，已否决** |
| **B-2 `caret-color` 收窄** | `components/style/global.less` L8 的 `caret-color: transparent` 从 `*` 收窄到组件自身作用域 | 1 行 | 真问题：会让宿主应用的 `contenteditable` 区域光标不可见（L29-32 仅豁免了 `input,textarea`） |
| **B-3 Resolver CI 断言** | 加一条校验：遍历 `getSideEffects()` 返回的所有路径，断言在 `es/` 下真实存在 | 2 小时 | 防「静默失效」（依赖升级后样式悄悄丢失且不报错）。**不改实现** —— 理由见 §4 C-6 |

### 3.4 保留方向但延后（有真实价值，非当前优先）

| 项 | 调整后做法 | 触发条件 |
|:--|:--|:--|
| **v-model 契约统一** | 保留方向（有真实 DX 价值，#44 即绑定值类问题）。但**砍掉 v1 的双轨过渡方案**，改为直接在 `3.0.0` breaking + 清晰迁移表。理由：双轨会引入 `value` / `modelValue` 两套 watch 互相触发的**竞态**，且过渡期代码复杂度翻倍，对一人维护是持续负担；8 个 dependents 的迁移成本本就可控 | 下次规划 major 版本时 |
| **a11y 批次 1**（纯补属性） | 为 Tabs（当前 aria/role/tabindex/keydown 计数为 **0**）、Select、Cascader、Collapse、Steps 补 `role`/`aria-expanded`/`aria-selected`；Modal/Drawer 补 focus trap。**纯增量、不改 DOM 结构、零回归风险** | 可作为低优背景任务，顺手做 |

| 契约 | 组件 | 数量 |
|:--|:--|:--:|
| `value` + `update:value` | Input / Textarea / InputNumber / InputSearch / Checkbox / Radio / Slider / Rate / Segmented / Tag / ColorPicker | 11 |
| `modelValue` + `update:modelValue` | Select / Cascader / Switch | 3 |

## 4. 已否决项及理由（完整记录）

保留此章的目的：**否决不等于遗忘**。每项标注「重新激活的触发条件」，便于未来条件变化时快速复用 v1 的分析。

### C 类：投产比为负或极低（6 项）

| # | v1 建议 | 否决理由 | 重新激活条件 |
|:--:|:--|:--|:--|
| C-1 | **a11y 批次 2/3**：Button `div→button`、Checkbox/Radio 原生化（3~4 周） | ①45 条 issue **零 a11y 反馈**；②371 star 个人库无合规压力；③Button 516 行样式全基于 `div` 编写，换 `<button>` 会引发**难以测出的细节视觉回归**。3~4 周换零用户可感收益 + 高回归风险 = **净负值** | 出现政企/金融/教育类客户的明确 WCAG 合规诉求 |
| C-2 | **i18n 机制**（1 周） | 零反馈，45 条 issue **全中文提出**。README 有英文版 ≠ 有海外用户 | 收到第一个多语言诉求 issue |
| C-3 | **全局 reset 改 opt-in** | **v1 最该被推翻的一条**：①Ant Design / Element Plus **都带全局 reset**，这是组件库常规做法而非缺陷；②仅 **3/66** 组件自带 box-sizing，改造需先动 64 个文件 + 全量视觉回归；③改完后**存量用户升级即视觉破损**。成本极高 + 收益可疑 + 风险大 | 收到明确的「reset 污染宿主样式」类 issue |
| C-4 | **巨型组件拆分**（Table 2145 行 / ColorPicker 1213 / Slider 1091 / Tabs 945） | 无用户反馈、不产生用户价值、一人维护下拆分反而**增加跳转成本并破坏作者已有心智模型**，短期改 bug 效率下降。属"显得专业"型改造。**唯一保留 `Result.vue`** —— 178 个内联 `<path>` 全量打进 JS 有真实体积成本，且它是纯展示组件、风险最低 | Table 出现多次难以定位的耦合 bug，或引入第二位维护者 |
| C-5 | **ESLint 规则回收**（8 条 off→error） | 会产生数百条一人清不完的 warn 噪音。关闭 `no-explicit-any`/`no-unused-vars` 等是作者的**主动权衡**而非疏忽（`vue/multi-word-component-names: off` 对组件库本就合理，其余同理） | 引入第二位维护者，或代码质量出现可归因于此的实际事故 |
| C-6 | **Resolver 改标准包名路径**（v1 的"推荐方案 A"） | 重新论证后认为**可能是错的**：①当前产物路径已确认有效并随包发布；②作者 `devDependencies` **自引用** `vue-amazing-ui@2.4.26`，`publish.sh` 中还有 `pnpm up vue-amazing-ui@$version` —— 升级依赖后若样式丢失他自己项目会立即暴露，「静默失效」风险**已被自我依赖机制对冲**；③改成 `swiper/swiper.css` 这类裸包名路径，在 **yarn PnP / pnpm 严格隔离 / hoisting 异常**场景下**反而可能解析失败**。净风险为负 | 改用 npm/yarn 构建，或产物路径结构发生变化 |

| # | v1 建议 | 判定 |
|:--:|:--|:--|
| D-1 | ConfigProvider 双清单同步风险 | 已实测**零漏项**。250+ 版本迭代下从未出错，恰恰证明手工同步在此规模下**有效**。收益 ≈ 0 |
| D-2 | 三函数重复实现（`getColorPalettes`/`isStableColor`/`getAlphaColor`） | 确实重复（约 20 行），但零 bug 风险、零用户影响。洁癖级优化 |

### 保留观察（不改，但记录）

- **`toggleDark`**（`utils/index.ts` L299-308）：仅切 class，注释里让用户自写 `filter: invert(1) hue-rotate(180deg)`。该 hack 会反转图片色彩需二次反转，全库 0 处 `prefers-color-scheme`，**并未真正支持暗色主题**。建议**仅在文档标注为「实验性」**，不投入建设真正的 dark token 体系（涉及 66 个组件样式，成本过高）。若 #35 的「全局主题」诉求推进，可一并评估。
- **commit type 使用不准**：如 Scrollbar 默认值调整属 `fix`/`refactor` 却标 `feat`。已有 commitlint 约束 type 枚举，但无法约束语义准确性。A-3 移除默认 message 后会自然改善。

## 5. 改造后的隐藏风险清单

v1 几乎未评估此项。以下风险适用于**任何**决定推进的改造：

| 改造 | 隐藏风险 |
|:--|:--|
| Button `div → <button>` | UA 默认样式（`font` 不继承、内建 `padding`/`border`/`background`、`line-height` 差异、`display: inline-block`）与现有 516 行样式冲突。此类回归特征是**"看起来正常但每个细节都偏了"**，人工与快照测试都极易漏过 |
| Checkbox/Radio 原生化 | ①改变**表单提交行为**（原生 input 自动参与 `<form>` 提交，属行为变更）；②`appearance: none` + 伪元素在旧 Safari 有兼容问题；③需同时重写视觉层与 `:checked` 状态链 |
| 全局 reset opt-in | 全库 **127 处 `:deep()`**（36 文件），scoped + deep 组合下补 box-sizing 会影响子组件继承链；且移除 reset 后**存量用户一升级即视觉破损**（其项目本就依赖这份 reset） |
| v-model 双轨过渡 | `value` 与 `modelValue` 两套 watch **互相触发的竞态** —— 双轨方案最经典的实现陷阱。故 §3.4 改为直接 breaking |
| Resolver 改标准路径 | 见 §4 C-6，**可能比现状更脆弱** |
| 加重 CI 门禁 | **拖慢发布节奏**。当前月均 6 版本、issue 响应及时（9/12 completed）。门禁越重，bug 修复到发布链路越长 —— 对小库，**快速响应本身即核心竞争力**，这是真实机会成本。故 A-3 只加 type-check + test 两项轻量门禁 |
| 大规模引入测试 | 一人维护下的**测试腐烂**：写了 70% 覆盖率但不同步维护，会变成"绿灯的假象"，**比没有测试更危险**。故 A-2 限定为「每条用例对应一个已修 bug」 |
| 巨型组件拆分 | 破坏作者已建立的心智模型，短期定位/修改效率下降。`Table` 依赖 10 个组件，拆分期间任何中间态都可能引入难查的耦合 bug |
| SSR 初值改动（B-1） | `useMediaQuery` 初值从「同步真实值」变为「`false` + 挂载后更新」，调用方若在 setup 同步阶段读 `match.value` 会拿到 `false`。**执行前需 grep 全库调用点确认** |
