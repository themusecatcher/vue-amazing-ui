## 1. 改造总原则

1. **先建网，再动刀**：任何涉及行为/样式变更的改造，前置条件是该组件已有测试覆盖。没有测试就重构等于盲改（当前 0 覆盖率是最大约束）。
2. **止血优先于治理，治理优先于优化**：SSR 崩溃是「不可用」，Resolver 硬编码是「脆弱」，v-model 不统一是「不好用」—— 严格按此顺序。
3. **破坏性变更集中释放**：v-model 统一、Button 语义化等 breaking change 全部攒到一个 major（v3.0），中间版本保持向后兼容，避免用户频繁适配。
4. **每阶段可独立交付**：任一阶段结束时项目处于可发布状态，不留半成品。
5. **依赖顺序不可逆**：下方标注的「前置依赖」是硬约束，跳序执行会造成返工或线上事故（例：先做全局 reset opt-in 而不先补 box-sizing，将导致 64 个组件布局破损）。

## 3. 阶段 1：止血（`2.4.27`，1~2 天）

**目标**：消除「装上就崩」级问题，不引入任何 API 变更，可当天发 patch。

### 3.1 任务 1-A：SSR 安全化（P0）

**问题**：`setup()` 同步执行期直接读 `document`/`window`，Node 环境抛 `ReferenceError`。

需修改的 4 处：

| 文件 | 行 | 现状 | 改法 |
|:--|:--|:--|:--|
| `components/select/Select.vue` | 81-82 | `ref(document.documentElement.clientWidth)` | 初值 `ref(0)`，`onMounted` 内赋真实值 |
| `components/tooltip/Tooltip.vue` | 70-71 | 同上 | 同上 |
| `components/utils/index.ts` | 606-607 | `ref(window && window.matchMedia(q).matches)` | 初值 `ref(false)`，`onMounted` 内 `matchMedia` |
| `components/utils/index.ts` | 827 | `window.addEventListener('test', ...)` 在函数体同步执行 | 包 `typeof window !== 'undefined'` 守卫 |

要点：
- `window &&` 这种守卫**无效** —— Node 下 `window` 是未声明标识符，读取即抛错，必须用 `typeof window === 'undefined'`。
- Select/Tooltip 的 `viewportWidth/Height` 仅用于弹层位置计算，初值 0 在 SSR 阶段不渲染弹层，无副作用。
- `Modal.vue` L179/185、`Dialog.vue` L138/144、`Drawer.vue` L91/95 的 `document.documentElement.style` 操作位于 `watch` 回调内，**SSR 下不执行，无需改动**（避免过度修改）。

**影响面**：Tooltip 被 8 个组件依赖（BackTop / Popover / Ellipsis / Rate / FloatButton / Popconfirm / ColorPicker / Table），Select 被 5 个依赖（Table / List / Pagination / Calendar / Cascader）→ 修这 4 处可解锁约半数组件的 SSR 可用性。

**验收**：新建最小 Nuxt 3 或 `vite-ssr` 验证工程，`renderToString` 渲染含 Select / Tooltip / Table 的页面无异常。

### 3.2 任务 1-B：仓库卫生（P2）

1. `.gitignore` 追加 `docs/.vitepress/cache`（现有忽略了 `dist`/`es`/`lib`，遗漏了此项）
2. `git rm -r --cached docs/.vitepress/cache` 清出索引（38 个文件）
3. `scripts/*.sh` 中的 `git add .` 改为显式路径或至少前置 `git status` 确认 —— 当前三个脚本全用 `git add .`，是缓存文件被反复提交的直接原因

**验收**：`pnpm docs:dev` 运行后 `git status --porcelain` 输出为空。

### 3.3 阶段 1 风险

- 低。均为局部修改，无 API 变更。
- 唯一注意点：`useMediaQuery` 初值从「同步真实值」变为「`false` + 挂载后更新」，调用方若在 `setup` 同步阶段读取 `match.value` 会拿到 `false`。需 grep 全库调用点确认（预计仅内部响应式使用，无同步读取）。

技术选型：`vitest` + `@vue/test-utils` + `jsdom`（与 Vite 7 同生态，零额外配置成本）。

**测试优先级按「被依赖度」排序**，而非按组件复杂度 —— 依赖图（`resolver.ts` L75-102）已给出天然优先级：

|:--:|:--|:--:|:--|

每个组件的测试基线清单（可复用为模板）：
- props 默认值与全部枚举值渲染快照
- v-model 双向绑定（emit 事件名与 payload）
- disabled / loading 等状态下交互被正确拦截
- 卸载后无残留监听（配合 `useEventListener` / `useResizeObserver` 的 cleanup 校验）
- SSR 渲染不抛错（`@vue/server-renderer` 的 `renderToString`）

> 最后一条建议作为**全组件通用用例**批量生成 —— 一次性为 67 个组件建立 SSR 冒烟测试，成本低、收益高，且能防止阶段 1 的修复被后续代码回退。

### 4.2 任务 2-B：CI 流水线

新建 `.github/workflows/ci.yml`，PR 与 main push 触发：

```
lint → type-check → test（含覆盖率门禁）→ build → build 产物校验
```

其中「产物校验」是本项目特有的必要环节（见阶段 3），至少校验：
- `es/` `lib/` 下每个组件目录存在 `index.js` / `index.d.ts`
- `resolver.ts` 中 `componentsMap` 的每个路径在 `es/` 下真实存在（可捕获硬编码路径失效）
- `npm pack --dry-run` 文件数不出现异常膨胀

### 4.3 任务 2-C：静态检查回收

分两步走，避免一次性引入上千条报错：

**第一步（本阶段）**：把关闭的规则改为 `warn` 并统计基数
- `eslint.config.js` L29-32：`no-explicit-any` / `no-unused-vars` / `no-unused-expressions` → `warn`
- `tsconfig.app.json` L28-29：解开 `noUnusedLocals` / `noUnusedParameters` 注释
- vue 规则档位从 `flat/essential` 升至 `flat/strongly-recommended`

**第二步（阶段 6 内滚动清理）**：按模块分批降为 `error`，每清完一个模块即锁定。

保留判断：`vue/multi-word-component-names: off` 应**保留** —— 组件库导出 `Button`/`Table` 等单词名是合理设计，不属缺陷。

### 4.4 任务 2-D：发布流程加门禁

`scripts/publish.sh` 当前流程存在明确风险：

```
pnpm build → git add . → git commit → git push → npm publish
```

无 lint / 无 type-check / 无 test / 无 tag，直接 publish。历史提交中三条同名 commit（`02035d7d`/`7092a4ae`/`179eac81` 均为 "optimize Scrollbar, adjust default autoHide..."）即缺少门禁的表征。

改造点：
1. `npm publish` 前串联 `pnpm lint && pnpm type-check && pnpm test`
2. 增加 `git tag v$version` 与 `--dry-run` 预演开关
3. 移除默认 commit message `'feat: update components library'` —— 强制传入语义化描述，否则退出。这是 2532 次提交里大量无信息量 commit 的根因

**验收**：CI 全绿为 PR 合并的硬性条件；`publish.sh` 在任一检查失败时中止且不产生任何 git 操作。

## 5. 阶段 3：解耦治理（`2.6.0`，1~2 周）

**前置依赖**：阶段 2 完成（尤其是「产物校验」CI 与 9 个基础组件的测试）。

### 5.1 任务 3-A：Resolver 去硬编码（P1）

**精确问题定位**（已校准）：`components/utils/resolver.ts` L119-141 的路径**当前有效**（产物存在且随包发布），真实风险是三重耦合：

1. **版本号硬编码**：`@vuepic_vue-datepicker@12.1.0_vue@3.5.29_typescript@5.9.3_`、`swiper@12.1.2` 写死在源码里。升级依赖后产物路径变化而 resolver 不变 → **静默失效**（无任何报错，只是样式丢失），这是最危险的失效模式。
2. **包管理器实现细节泄漏**：路径含 `.pnpm` 与依赖哈希后缀，若作者切换 npm/yarn 构建，结构完全不同。
3. **规范风险**：包内嵌套 `node_modules` 目录属反模式，部分 CI 的 prune 步骤、yarn PnP、以及部分 CDN 对包内 `node_modules` 处理不一致。

**改造方案（推荐 A，备选 B）**：

- **方案 A（推荐）**：改用标准包名路径 `@vuepic/vue-datepicker/dist/main.css`、`swiper/swiper.css`、`swiper/modules/navigation.css`，由用户侧 bundler 解析。同时 `vite.config.ts` 停止将外部依赖 CSS 输出到 `es/node_modules`（体积同步下降）。
  - 代价：要求用户项目中存在这两个依赖。当前它们是 `dependencies`（`package.json` L74/79），安装库时会自动装上，**用户侧一定可解析**，无实际代价。
  - 收益：彻底消除版本耦合与包管理器耦合。
- **方案 B（保底）**：保留产物内联，但路径从构建时**自动生成**而非手写 —— 构建后扫描 `es/node_modules` 实际路径，生成 `resolver.generated.ts`。
  - 适用于必须保证零外部依赖解析的场景，但复杂度更高。

**配套守护**：阶段 2 的 CI「产物校验」增加一条 —— 遍历 `getSideEffects()` 返回的所有路径，逐一断言在 `es/`（或用户可解析范围）内存在。这是防止此类问题复发的根本机制。

### 5.2 任务 3-B：全局 reset 改 opt-in（P1）

**问题**：`components/style/global.less` 通过 `components/index.ts` L1 与 `resolver.ts` L113 **强制注入**，作为组件库对宿主应用施加：
- L2-9 `*, *::before, *::after` 清零全部元素 margin/padding，破坏宿主既有排版
- L8 `caret-color: transparent` 应用到 `*`，仅 L29-32 豁免 `input,textarea` → 宿主的 `contenteditable` 区域光标不可见
- L14-28 覆写 `body` 的 `font-family`；L33-44 覆写全局 `a` 样式

**关键前置约束（必须先做，否则布局大面积破损）**：

复验发现 **仅 3/66 个组件自带 `box-sizing`**，即 **64 个组件的布局隐式依赖全局 reset**。因此改造必须严格按序：

```
步骤 1：为 66 个组件的 scoped style 补齐自洽的盒模型基线
        （在各组件根选择器下声明 box-sizing: border-box 并覆盖后代）
步骤 2：视觉回归验证（借助 docs 站点 67 个组件页做截图对比）
步骤 3：global.less 拆分为 reset.css（opt-in）+ tokens.css（CSS 变量，必需）
步骤 4：components/index.ts 与 resolver.ts 仅注入 tokens.css，reset.css 改为文档引导用户按需引入
步骤 5：`caret-color: transparent` 从 `*` 收窄到组件自身作用域内（其目的是消除 Win 下点击闪烁，只需作用于组件内非输入元素）
```

> 步骤 1 是 64 个文件的机械改动，建议在阶段 2 的组件测试覆盖到位后进行，并逐组件小批提交（每批 ≤ 8 个组件），便于回滚定位。

**破坏性说明**：对依赖了本库全局 reset 的存量用户，这是行为变更。需在 `2.6.0` release note 明确告知，并提供一行 `import 'vue-amazing-ui/reset.css'` 的兼容路径。

### 5.3 任务 3-C：主题系统去重（P3，已降级）

**校准后的真实问题**（无功能 Bug）：

1. **三函数完整重复**：`getColorPalettes` / `isStableColor` / `getAlphaColor` 在 `ConfigProvider.vue` L292-311 与 `utils/index.ts` L777-809 各实现一份，逻辑一致。→ 统一由 `utils` 导出，ConfigProvider 引入。
2. **双清单手工同步**：`Theme` 接口（L10-102，31 个组件）与 `componentsThemeColor`（L124-249，31 个组件）为两份平行手写清单，**当前完全一致无漏项**，但每新增一个支持主题的组件需人工改两处，是明确的未来出错点。
   → 改法：定义 `THEMEABLE_COMPONENTS` 常量数组作为单一来源，`Theme` 类型用映射类型派生（`Record<typeof THEMEABLE_COMPONENTS[number], { primaryColor?: string }>`），`componentsThemeColor` 用 `reduce` 生成。约减少 220 行样板代码。
3. **可选增强**：为 `useInject(key)` 的 `key` 参数加上字面量联合类型约束，使传入未注册组件名时**编译期报错**而非静默 fallback —— 这能从类型层面根除「漏注册」类问题，替代人工校验。

## 6. 阶段 4：API 统一（`2.7.0` 过渡 → `3.0.0` 落地，2~3 周）

**前置依赖**：阶段 2 完成（v-model 行为变更必须有测试兜底）。

### 6.1 现状分类（已确证）

| 契约 | 组件 | 数量 |
|:--|:--|:--:|
| `value` + `update:value` | Input / Textarea / InputNumber / InputSearch / Checkbox / Radio / Slider / Rate / Segmented / Tag / ColorPicker | 11 |
| `modelValue` + `update:modelValue` | Select / Cascader / Switch | 3 |
| `defineModel()` | Calendar | 1 |
| **同时 emit 两种** | Checkbox（`update:value` + `update:checked`）、Radio（同） | 2 |

用户必须逐组件查文档才知道写 `v-model` 还是 `v-model:value`，是本库最高频 DX 陷阱。

### 6.2 双轨过渡策略（避免一刀切 breaking）

**`2.7.0`（兼容期）**：
1. 全部 15 个组件统一改用 `defineModel()`，标准契约为 `v-model`（`modelValue`）
2. 同时保留 `value` prop 与 `update:value` emit 作为**别名**，内部双向同步
3. 使用旧契约时通过 `console.warn` 输出 deprecation 提示（仅 dev 环境，用 `import.meta.env.DEV` 包裹，避免污染生产）
4. 文档为每个组件标注「推荐 / 已废弃」两种写法

**`3.0.0`（清理期）**：移除 `value` / `update:value` 别名与 warn 逻辑。

### 6.3 特殊处理

- **Checkbox / Radio 的 `update:checked`**：语义与 `update:value` 不同（单选状态 vs 选中值），需先确认二者是否真为冗余。若是同一语义 → 合并；若确有区分（如 Checkbox 单体 checked 与 group value）→ 保留但改名为语义明确的 `v-model:checked`，并在文档中说明二者关系。**此项需先读全 Checkbox.vue L32/69/75 与 Radio.vue L35/68 的完整逻辑再定，不可预设结论。**
- **Calendar** 已用 `defineModel('value')`，命名为 `value` 而非默认 `modelValue`，需一并对齐。

### 6.4 风险

- **中高**。这是对外 API 的破坏性变更，影响所有存量用户。
- 缓解措施：双轨期至少跨 2 个 minor 版本（约 2~3 个月）；提供 codemod 脚本或详细迁移表；`3.0.0` 发布前在 README 与文档站顶部持续挂公告。

## 7. 阶段 5：能力补齐（a11y + i18n，3~4 周）

**前置依赖**：阶段 2（测试）+ 阶段 4（避免与 v-model 改造在同文件冲突）。

### 7.1 任务 5-A：i18n 机制（P1，建议先做 —— 改动可控且无视觉风险）

**现状**：全库零 i18n 机制，中文写进 props 默认值：
`Modal.vue` L41/43、`Dialog.vue` L45/47、`Popconfirm.vue` L33/36（`'取消'`/`'确定'`）、`Select.vue` L41、`Cascader.vue` L42（`'请选择'`）、`Empty.vue` L13（`'暂无数据'`）。

**改造设计**：
1. 新建 `components/locale/` 目录，定义 `zh-CN.ts` / `en-US.ts` 与 `LocaleConfig` 类型
2. `ConfigProvider` 增加 `locale` prop，与现有 `theme` 同机制 `provide`
3. 新增 `useLocale(componentName)` 组合式函数，与 `useInject` 对称（复用其「组件级覆盖 → common → 默认」三级 fallback 逻辑）
4. 组件内 props 默认值由硬编码字符串改为 `undefined`，渲染时 `props.okText ?? locale.okText`

**兼容性**：默认 locale 仍为 `zh-CN`，显式传 props 的行为不变 → **非破坏性变更**，可在 minor 发布。

**范围界定**：先覆盖上述 6 个组件，再扫描 Table / Pagination / Upload / Calendar / DatePicker 内部生成的文案（这些是用户无法通过 props 覆盖的部分，收益最大）。

### 7.2 任务 5-B：a11y 专项（P1，工作量最大，建议分批）

**现状量化**：29/67 个组件含 `aria-`/`role`/`tabindex`，17 个组件有键盘事件；Tabs（945 行）的 aria/role/tabindex/keydown 计数为 **0**。

**根因**：所有交互组件根元素为 `div`（已逐一确认 Button / Checkbox / Radio / Switch / Select / Input 的 `<template>` 首元素均为 `div`），导致语义、焦点、键盘、表单集成需全部手工模拟。Button 的实现即典型：

```
components/button/Button.vue L85-87  <component :is="href ? 'a' : 'div'" tabindex="0">
components/button/Button.vue L117    @keydown.enter.prevent="..."
```

手工补了 `tabindex` 与 Enter，但仍缺：**Space 键触发**（已确证全文件仅有 `keydown.enter`，无 space）、`aria-disabled`、disabled 时 `tabindex="-1"`（当前禁用按钮仍可 Tab 聚焦）、`<form>` 内 submit 行为。

**分批策略（按「改造成本 / 收益」排序）**：

| 批次 | 范围 | 具体动作 | 风险 |
|:--:|:--|:--|:--|
| 1 | 低风险补属性 | 为 Tabs / Select / Cascader / Collapse / Steps 等补 `role` / `aria-expanded` / `aria-selected` / `aria-controls`；为 Modal / Drawer / Dialog 补 focus trap 与 `aria-modal`；为 Select / Cascader / Tabs 补方向键导航 | 低（纯增量，不改 DOM 结构） |
| 2 | Button 语义化 | `div` → `<button type="button">`，补 Space 键、`disabled` 原生属性、`aria-disabled` | **中**：`<button>` 有浏览器默认样式与 `display: inline-block` 差异，需同步调整 scoped 样式并做视觉回归 |
| 3 | 表单原生化 | Checkbox / Radio 改为 `<input type="checkbox/radio">` + `<label>` 关联（视觉层用 `appearance: none` 或伪元素）；Switch 改 `<button role="switch" aria-checked>` | **高**：涉及 DOM 结构重写 + 样式重写 + 表单集成语义变更，属 breaking，需进 `3.0.0` |

**建议**：批次 1 在 `2.8.0` 发布（非破坏性，立即提升合规度）；批次 2、3 合入 `3.0.0` 与 v-model 破坏性变更同批释放。

**验收标准**：引入 `axe-core` / `eslint-plugin-vuejs-accessibility` 做自动化审计，把「无 critical 级违规」纳入 CI；键盘可达性用 Playwright 做 Tab 序列断言。

## 9. 阶段 7：长效机制（持续）

单次改造无法防止问题复发，需建立机制：

1. **契约守护测试**：
   - v-model 契约一致性：遍历所有表单组件断言均 emit `update:modelValue`
   - 主题注册完整性：断言每个 `useInject(key)` 的 key 都在 `THEMEABLE_COMPONENTS` 中（阶段 3 完成后此项由类型系统保证，可省）
   - Resolver 路径有效性：断言 `getSideEffects()` 所有返回路径真实可解析
   - SSR 冒烟：67 个组件全量 `renderToString` 不抛错
2. **文档与代码同源**：67 个组件文档已 100% 覆盖（`docs/guide/components` 计 67 项，与组件数一致），但 props 表需人工同步。可评估从 `Props` 接口自动生成 props 文档表。
3. **提交规范收紧**：已配 commitlint + husky，但 type 使用不准（Scrollbar 默认值调整属 `fix`/`refactor` 却标 `feat`），且大量 `feat: update components library`（来自 `scripts/*.sh` 默认值，已在阶段 2 移除）。补充：约定 `type` 选择指引写入 `CONTRIBUTING`。
4. **依赖升级流程**：因 Resolver 曾与依赖版本耦合，需固化「升级 datepicker/swiper 后必跑产物校验 CI」的检查项（阶段 3 方案 A 完成后此耦合消除，可降级为常规检查）。
